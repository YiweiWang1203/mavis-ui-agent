# 用户任务驱动的六步优化

适用：用户要求边验证边优化系统、制定优化目标或评估一轮优化效果。每轮围绕一个可检验的优化假设推进。普通改字、格式调整不必套用完整实验。

## 每轮固定六步

1. **确认用户失败。** 写清原始要求、用户想完成的操作、当前实际结果及影响。引用输入和运行证据；源码线索与实际操作结果分别记录。先描述问题，再选择技术方案。不能从模型输出反推原需求。
2. **定位原因。** 跟踪信息从输入、解析、融合、布局到实现和运行的去向，区分已证实原因与待检验假设。不要直接把每种失败都归因于提示词，也不要先增加Agent或依赖。

   生成链路缺少中间证据时，先补埋点再选功能改动。除模型请求/响应外，还要记录规范化、融合、先验、布局的前后状态、元素增删与属性变化原因，区分模型错误和系统代码引入的错误。埋点应不改变原行为、不新增隐式重试；已有日志的诊断重建不能冒称历史实时记录或生成效果验证。先统一实验入口与正式入口的版本，不能把未执行的ASR、选帧等步骤当作已验证。参考其他Agent时核对其实际失败率、反馈机制和调用预算，不预设他人系统零错误。
3. **提出优化假设。** 用一句话说明“通过X机制改善Y失败，因为Z”。列出预期现象及能够否定假设的结果；技术手段不是用户目标。
4. **固定方案与目标。** 先测基线，再规定主指标、分子分母、通过条件、退化约束和资源上限。没有基线时不编造“提升20%”。区分工程验收、跨案例效果与泛化；百分比和百分点不混用。一次改一个机制，可涉及多个文件。
5. **实施并对照验证。** 改代码前保存相关旧文件、差异、输入与版本哈希。保留原始响应及产物，在新目录保存候选结果。使用相同输入、要求、浏览器环境和可比资源验证；先小规模复现/回归，阶段结束再跑完整对照。对浏览器交互问题必须实际操作，不能用动作名、事件绑定或任意alert代替目标效果。只使用已有授权，不因调用本技能而扩大远端、外部通信或付费调用权限。
6. **决定下一步。** 对照预定目标报告达标/部分有效/无效/证据不足，以及退化、代价、未解决问题；决定保留、修订或回退。不挑最佳运行、不掩盖首次失败。连续尝试仍不能解释失败时重新定位，不无限重试。

## 优化卡（每轮一份，实施前写前半部分，验证后补结果）

- 轮次、状态、代码/输入版本：
- 用户任务、失败及来源证据：
- 原因：已证实事实 / 待检验假设：
- 优化假设及机制：
- 方案范围与不改变的条件：
- 基线、主指标及固定分母：
- 工程验收目标、跨案例验证、退化/成本约束：
- 原始产物、新产物、操作记录和测试位置：
- 实测结果与未达标项：
- 结论与下一轮：

## 研究与UI生成场景的关键边界

- 用户价值优先：完整可辨页面、要求的基本操作、内容保留和稳定获取结果。重复减少、代码更短或多了Agent只是机制/诊断，必须追踪到用户结果。
- 类型、动作声明属于结构证据；呈现、输入、点击与目标反馈属于运行证据。对未设计的新页面、后端或业务流程不擅自加要求；不同案例的原意澄清不能互相套用。
- 修复已保存输出的回放可隔离某一后处理机制，但不是端到端重新生成，也不证明新案例效果。标明回放、生成、恢复及开发案例的身份。
- 用过的案例仍可做回归，不称未见测试；正式效果需要冻结方法后在未用于调试的材料上验证。评测答案不能泄露给生成或修复环节。
- 旧稿、冻结基线、原始输入/ASR/评分不覆盖；更正另存版本。新稿仅按已确认事实写结果，待完成的GT确认、独立复核与浏览器验收不因冻结而自动完成。
- 用户问题变化、修复目标变化及资源增加分别说明。方法含额外调用时记录成本；若归因某个机制，设相同预算或相应消融，避免把多个变化揉成一个结论。
- 小修复可以是工程工作，不包装成独立论文创新。统计单位是案例/运行，不把同页大量控件当独立样本。

## 生成系统的有效性边界与版本循环

本项目评价的是系统从案例输入重新生成的可行性与表现。禁止把手工修改或脚本修复已保存HTML后的效果当作系统优化成果；旧产物回放只能定位原因或检查实现，不能作为本轮优化验收、论文提升或停止工作的依据。系统内自动后处理若确有必要，也必须在真实生成链路中启用并重新生成验证，原始响应与处理结果分别留存。本项目当前优先改真实生成链路，不继续推进旧HTML修补方案。

每轮执行以下六项版本循环，与上面的研究六步配合：
1. 记录用户失败、优化假设、验收指标、退化约束与预算。
2. 修改真实生成路径，做必要的本地工程验证；模拟调用只能证明接入正确，不能证明生成效果。
3. 按可验证的小版本提交并推送优化分支，限定本轮文件，检查凭据与无关材料；不把整个脏工作区一起提交。遵循现有提交身份，不冒称人工完成。仅在用户已授权提交推送时执行。
4. 提供Ubuntu同步和重跑命令，核对远端改动与实际提交编号，避免覆盖已有实验环境。必要时新建独立检出目录并复用原有UV环境。用户负责运行远端实验时，工作推进到代码已推送、命令可执行后交接；推送受阻则明确报告，不能宣称就绪。
5. 原版和候选版从相同案例输入重新生成，固定模型、预算、浏览器与评分规则；独立保存请求、响应、输入和代码哈希、失败及产物。禁止读取标注答案指导生成。旧输出与新输出只作探索比较，正式归因需要可比的新对照。
6. 根据真实新生成结果决定保留、修改或回退；没有提升也记录。推送不等于Ubuntu已同步，工程测试通过不等于实验有效。

## 启动与交付

任务已授权时直接执行能独立推进的工作；只在原意、关键约束确实缺失时集中询问，并继续无依赖的检查。每轮给用户简明说明：问题、假设、预定目标、实际改变、验证结果、限制及下一步。未执行的优化或远端运行必须明确标注。
