# 链路诊断与Agent架构优化依据

本轮先补可观测性，不把提示词当作默认优化对象。研究目标仍是用户意图被保留并落实为可用页面；记录完整不等于页面变好。以下研究为定向查阅论文、官方项目说明与公开入口源码，未安装或复现外部系统，不能称全领域系统综述。

## 当前系统的实证问题

实验入口run_pilot_experiment.execute和生产入口run_video_ui_workflow.py不同。前者直接复用冻结图片与FunASR转录，后者经输入适配器和图节点调度；不能将前者一次重跑称为从视频到页面全部步骤重新执行。图节点还有额外状态路由和视觉模式配置，需逐项确认，不能将图中的Agent名称直接当作实际执行次数。

现有模型原文只能回答模型说了什么，不能解释系统随后改了什么。已对最近六组保存的架构响应做零API诊断重建，六组最终UI-State均与当时记录相同。这说明新埋点可解释确定性转换；不是重生成或优化效果证据。

008两组都在geometry_merge从16变成32，priors与layout不再增数。原因是架构模型换了所有id，视觉id与架构id交集为0，按id补遗漏的逻辑将16个视觉元素再次补入。下一层不知道这是两个证据源的同一元素，便继续排版和生成。应优先修正身份与来源契约，而不是只给Coder增加约束。

新埋点还定位到第二个确定性问题：008融合后越界框为0，布局后原版20个、候选24个框超出375×812画布。重建结果与原记录一致，所以这是旧批次实际存在的结构结果，不是埋点新增的变化。数量膨胀发生在融合层，越界发生在布局层；不能合并归因于Coder或提示词。越界计数是结构诊断，不是按用户需求计算的页面得分。

002的电脑要求在架构输出时就可能变成手机画布；布局/代码无法从已经错误的画布自动保证正确。003则说明控件存在、id匹配、实际可点可输是三个不同检查，不能用其中一个代替另外两个。

另一个版本问题：Git已提交的预处理orchestrator保留ASR占位，本地和原Ubuntu项目有实际实验所用的真实ASR改动。本轮不覆盖这部分已有工作，不让诊断分支中的旧视频入口替代原项目。先清点入口、真实执行路径和版本，再统一部署；不能仅因目录名字相同就假定代码一致。

## 现有研究怎么搭建，哪些值得借鉴

| 工作 | 原文支持的方法 | 对我们的意义与边界 |
|---|---|---|
| WebGen-Agent | 代码执行、截图反馈与GUI交互测试进入迭代轨迹，错误累积后回退，末尾按预定规则选择版本；官方入口显式设置迭代和错误上限 | 需要运行反馈与失败隔离，而非仅串联模型。其Claude-3.5-Sonnet相关accuracy为51.9%，不是零错误；预算、训练、任务不同，不能横比我们的13例 |
| WebVIA | 探索阶段记录截图、DOM和操作形成状态转移图，生成后执行任务验证；论文也使用专门训练模型 | 借鉴“操作→预期状态”的证据组织；我们的单页按原始意图验证，不擅自要求新页面或完整业务后端，不能直接照搬其多状态输入 |
| MM-WebAgent | 先全局布局规划，再局部多模态元素规划，分别做局部、上下文和全局反思 | 全局画布、结构层级和局部控件应有清晰职责。它侧重图片/视频/图表整合，不是我们口述草图任务的直接对照 |
| WebUIProof（2026-10预印本） | 使用结构化需求与可执行交互断言，浏览器计划—操作—观察循环；报告页面能渲染时仍有大量交互失败 | 需要真实执行与明确断言；不能用HTML闭合、事件名或模型自评分代替功能完成。其基准输入与任务范围不同，不能直接搬用分数 |

这些工作共同提示的是：错误需要被观测、执行验证和有界处理。它们不能证明“多Agent天然正确”。我们的改动尚未启用自动修正或回退；参考的方法必须另做成本可比的对照。若采用best-step选择，要预先定义规则、保存全部尝试并计入成本，不能事后只挑最好的一次。

## 建议架构及优化顺序（待验证方案，不是已实现效果）

1. **统一结构身份和来源。** 建立稳定元素id与source_refs，视觉证据和口述新增需求分开引用。对同一对象的跨源信息做明确融合，无法确定对应就报告未决；既不能按名字随意合并，也不能把所有未匹配元素都当作缺失再补一遍。先解决008中已证实的链路问题。
2. **把不变量变成层间校验。** 输出JSON可解析只是第一步；还要检查id唯一、来源有效、画布与明确设备要求一致、坐标单位明确、输入类型合法。发现异常先定位和标记，不悄悄夹到1像素后继续传递。不默认增加新Agent。
3. **分离证据几何与渲染几何。** 保留原图坐标、转换关系和布局调整原因。布局层负责排版，不能顺便重新解释内容或丢弃需求。用新埋点测每一层究竟改变多少元素、哪些坐标、是否越界。
4. **验证组件语义落实。** 结构输入对象、DOM原生控件、可点击可输入分别验收。评估受控组件生成与自由HTML生成的取舍；不能直接宣布确定性渲染优于LLM，也不把旧产物修补当作证据。
5. **最后建立有界运行反馈。** 执行新生成页面，收集DOM、截图、控制台异常与操作后的状态。失败归属哪一层，就定向重执行哪一层；调用次数和停止条件预先固定。页面修改必须作为系统流程的一部分重新生成、留存全部版本并正式验证。

优先级依据是最早破坏用户需求的层，而不是论文里哪个方法名称更新。标注答案只用于评估，不喂给生成/融合/修复。13例都是开发回归材料，不能标成未见泛化验证。

## 本轮埋点范围与限制

已加入独立追踪上下文、前后快照、变更清单、融合决策、失败类型、耗时和哈希；覆盖生成实验的视觉解析/规范化/验证、架构解析/融合/先验/布局、Coder输入/输出与静态DOM契约检查。预处理各组件和输入适配器也有可选埋点，需通过trace_workflow入口启用；本轮冻结案例不会执行它们。ASR占位入口问题尚待版本统一，不能宣称视频全链路验证完成。

图像和音频本体沿用原有阶段产物，日志保存路径和结构内容；冻结案例另存输入字节和SHA256。浏览器仍是独立执行的验收环节，不在生成函数中假装自动通过。静态DOM报告明确标记static_only_not_behavior_score。

本轮不改变功能行为、提示词、模型或重试预算；新增的是诊断能力。下一步先用008做一次baseline真实运行确认日志完整，最多3个模型请求，再依据证据选择首个功能修复，不同时混入所有架构建议。
