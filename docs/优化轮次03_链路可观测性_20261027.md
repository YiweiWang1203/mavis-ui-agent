# 轮次03：先观测链路，再选功能优化点

本轮目标是诊断能力，不能写成页面生成效果提升。不开新提示、不换模型、不改预算、不自动修复HTML、不新增模型调用。先明确模型与系统代码分别做了什么。

已有运行只保存模型请求/响应、视觉验证结果、最终UI-State和HTML，融合、先验、布局中间态缺失。008的16→32说明不能仅把最后失败归因于模型提示。

方案：启用独立追踪上下文，保存每层完整输入与输出、逐元素属性差异、增删编号、画布变化、坐标越界、异常类型和耗时。融合层另记每个元素为什么保留、丢弃或补入。不开追踪时直接走原函数；开启追踪只观察，不改变输入输出、不引入隐式重试或修复。失败记录保留，不记录配置环境或异常中的凭据。

当前实验主线：固定案例输入→图像编码→视觉模型原文（call记录）→视觉解析→规范化→编号重排→视觉验证→架构模型原文→JSON解析→视觉几何融合→先验规则→布局求解→Coder输入→模型原文→去围栏→最终HTML→独立浏览器检查。浏览器评分继续另存，不把静态检查或模型自评当作真实操作成功。

视频预处理与冻结案例生成是两个入口。冻结案例重跑必须明确ASR、选帧、旋转等本次未执行；不得把复用的转录当成本轮新ASR。视频入口的步骤输出也需要记录，但不能冒称旧版本缺失的记录已补齐。已有预处理包可以帮助回溯，仍需区分当时保存和事后推导。

本地与Git的预处理版本存在差异：当前已提交orchestrator仍是ASR占位，工作区已有真实ASR接入且未提交。本轮不覆盖这些已有改动，不让用户通过这次诊断分支切换到旧占位入口跑新视频；视频入口版本统一需另行检查。新案例实验当前继续使用原项目既有真实转录与选帧。

预定验收：同一模拟响应下开启/关闭埋点，返回值和下游请求一致；嵌套追踪不串运行；失败日志保留且不泄漏异常文本；阶段输出不因后续修改被覆盖；重复id不被统计字典吞掉。对上一批已保存的架构输出执行诊断复现，只验证定位能力，不生成、修复或重评HTML，不声称效果提升。随后用一次Ubuntu真实生成确认各层记录确实落盘，再决定第一个功能优化点。
