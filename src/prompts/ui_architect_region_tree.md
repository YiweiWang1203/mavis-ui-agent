Design a UI from the original request, numbered fresh ASR segments, target platform and vision evidence. First list the actionable spoken UI requirements individually, then design and bind them. Keep requirements whose meaning or object binding is uncertain and mark them unknown. Use segment IDs only, including multiple IDs when needed. Source excerpts are computed by the caller.

Use the target_size when consistent with explicit user intent. Photo geometry is evidence only. Keep observed controls distinct and preserve their IDs and supported labels and actions. Correct an observed type when original evidence supports a different control type. Keep its visual ID, set origin to both when speech supports the correction, and bind the supporting numbered segments to that object in requirements. Add explicitly requested spoken-only controls where appropriate. Use short stable IDs. Use the tree to implement each supported region, its membership and its local direction. A row's children run left-to-right and a column's top-to-bottom. Use a nested region when a subset has a different axis. Put a bottom group under the region it belongs to, as that column's last child, with slot "bottom". A local bottom group does not mean viewport-fixed. Avoid unused or invented regions.

Return only a JSON object with page_meta, requirements, elements and region_tree.
page_meta.viewport contains positive integer width and height chosen from the target evidence.
Each requirement contains sources (numbered segment IDs), intent (text), certainty, status, scope, targets (IDs) and references (IDs).
Each element contains id, type, text, rpa_action and origin. Elements hold business properties.

Tree node shapes are mutually exclusive:
- A region has id, axis ("row" or "column"), a nonempty children array and optionally slot. Its id must be distinct from every element ID. The root region has id "page". Choose its axis from the required arrangement of its immediate children; neither axis is a default.
- A leaf has only id and optionally slot. Its id references exactly one inventory element. It must never have axis or children. A composite control needs a separate region wrapping the native input leaf and its button leaves. Do not reuse an input's ID as its enclosing region.
- slot may be omitted or have the sole value "bottom". It is permitted only on the last child of a column region. Do not emit top, middle, left, right or any other slot value. Express ordinary positions through the appropriate parent axis and ordered children. A bottom group may itself be a row, provided its parent is a column and it is the last child.

Each element occurs exactly once in the tree. Unknown requirements have status "unknown" and targets []. Bind to the involved element and region IDs as appropriate. Do not emit bounding boxes, parent IDs, order numbers, or a separate relationship table.

Certainty is explicit, inferred, or conflicting. Scope is the ID of the containing region that the requirement refers to, or null if unresolved. References are IDs of objects or regions used as reference points in the requirement. References and scope document intent and never place objects. One requirement can involve several objects, and an object may fulfill several requirements or have no spoken requirement. Mark element origin speech, vision, both, or request. Keep vision-only objects and support spoken-only objects. Return an empty requirements array if there are no actionable spoken requirements.

Use the actual local containing region for scope. Use page only when the source refers to the page as a whole. Keep reference objects when the requirement positions something relative to them. Before returning, check each bound requirement against the executable tree within its scope. Left/right requires the relevant branches to be ordered under a row; above/below requires a column. Region names alone do not establish direction. When different subsets require different directions, introduce the supported nested regions. Check that every bottom slot is attached to the intended local parent and that each inventory control remains a leaf. This is your own planning consistency check.
