Relation-first mechanism (opt-in spatial-relations-v1, same planning call).
Before choosing parents and row/column, identify the spatial relationships actually supported by User Intent or the immutable observation. Output top-level relation_plan BEFORE region_contract in this same JSON (not a second call):
{"version":"spatial-relations-v1","relations":[
 {"id":"rel_unique","kind":"left_of","subject":"existing_object_or_region_id","object":"another_existing_id","status":"proposed","evidence":[{"source":"asr","quote":"exact unique substring from supplied User Intent"}]}]}
The allowed kinds are left_of, above, contains. Express right_of/below/inside by reversing the endpoints. contains means the subject is an organizational region and the object is in its descendant subtree; it does not require an immediate parent. Endpoints reference existing planned IDs, never text labels or new business objects. Same-node and duplicate claims are invalid. For evidence use exactly the original schema's asr/sketch/model_inference items; quotes prove location, not meaning. A relation is always model-proposed or unknown, never confirmed. Do not label uncertain or conflicting original evidence as a certain relation just to pass code.

Then build the smallest tree that can express these relationships together. One parent's direction governs only its direct sibling sequence; it is NOT a global direction for every descendant. Local horizontal siblings inside a vertical group and a vertical subgroup beside another area require different nested organizational regions. Introduce only the necessary transparent semantic_region containers, with no business text/action/label, retaining each original object once. Do not force all objects at one depth, make equal partitions, or use the generic example as a template. Choose the tree from THIS input, not an assumed page category.

Cross-check the completed tree against your relationship list before returning. left_of/above between nodes in different subtrees is represented by their first divergent branches under the lowest shared ancestor: that ancestor must respectively be row/column, and the subject branch must precede the object branch. contains must follow ancestor reachability. If a local arrangement conflicts, reorganize the organizational tree before submitting, not the observation/source content. Do not remove a clearly sourced relationship just to preserve a convenient tree. The code only checks declared relationship/tree consistency; it cannot infer missing relationships from wording or certify the original meaning.

For uncertain relationships use status=unknown and retain the evidence/uncertainty; these are recorded, not enforced or promoted to facts. If no spatial relationship can be grounded, use an empty relations list and preserve uncertainty rather than inventing a rule. Unknown/empty claims do not count as source relationship coverage or success. Relation coverage and actual geometry are independently reviewed after generation. Conflicting proposed claims reject the plan without automatic tree repair, retries or a new model call. This mechanism changes ONLY spatial organization; it does not add behavior requirements, repair observed object types or invent missing business objects.
